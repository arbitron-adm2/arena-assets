# Протокол Wormix — сводка

Покрытые версии: **1.61.7** (полный разбор клиента и протокола), **1.63.3**
(ассеты + карта команд). Ниже — только проверенные факты; неизвестное вынесено
в раздел «Где ещё копать».

## Транспорт

TCP, без TLS. Один кадр = 7-байтный заголовок + тело:

```
byte 0      flags          база 0x57, биты 3/5/7 — шум
bytes 1-2   command id     бит 15 может быть выставлен как шум (маска 0x7fff)
bytes 3-6   body length    биты 30/31 могут быть выставлены как шум (маска 0x3fffffff)
body        payload + 16-байтный md5(payload || secret)
```

Инварианты приёмника: `flags & 0x57 == 0x57`, а биты 3/5/7 флагов обязаны
**отличаться** от бита 15 команды и битов 30/31 длины. Отправитель рандомизирует
эти три пары, поэтому кадры не побайтово постоянны.

Хвост — `md5(body || secret)`; секрет статический, в публичном репозитории
заменён на `<REDACTED_PROTOCOL_SECRET>`. Клиент отказывается принимать ответ
`ENTER_ACCOUNT`, если хвост не сходится.

Сервер не строго request/response: между ответами приходят незапрошенные
`ShowSystemMessage`. Поэтому ожидание ответа регистрируется по `command id`
до отправки, а всё несовпавшее складывается в `unsolicited`.

## Карта команд

- `protocol/commands/commands-1.63.3.json` — 262 id: `message` (имя из 1.61.7),
  `v1617`, `v1633`, `status` (`same` / `new` / `gone`).
- `protocol/commands/README.md` — та же таблица в читаемом виде.
- Итог: 171 id совпадает, **78 новых**, 13 исчезли; 184 id имеют читаемое имя.

Извлечение воспроизводится:

```bash
# 1.61.7 — FFDec -export script по клиенту, затем:
python3 tools/extract-command-ids.py --sources client/1.61.7/as3 --mode readable

# 1.63.3 — FFDec -export script, затем:
python3 tools/extract-command-ids.py --sources <export> --mode obfuscated
```

В 1.63.3 метод называется `§!S§()`, а id обычно лежит константой другого класса;
скрипт строит карту констант по всему экспорту и разрешает ссылку (250 из 258;
8 не разрешаются — id собирается в рантайме через `ID.value`).

## Что изменилось в 1.63.3 (наблюдения)

- `data/serializers.xml` (254 команды + 55 структур в 1.61.7) **отсутствует**:
  сериализаторы вшиты в клиент, внешнего файла нет.
- Клиенту обязательны flashVars `_social_type` (и `_app_key`, `_app_link`,
  `_app_mode`, `_upload_url`): без них `Application.onAddedToStage` получает
  `null` от фабрики соцконтроллера и инициализация обрывается.
- Баннер `Protected by secureSWF` — только текст (`DefineEditText`, tag 37):
  на исполнение не влияет, проверено сравнением с непатченным клиентом.
- Карты уровней (`levels/`) приходят от сервера: статического списка в клиенте нет.

## Что уже сделано по новым командам

- `protocol/commands/commands-detail-1.63.3.json` — все 250 id: класс, направление
  (`reads` -> ответ сервера, `writes` -> запрос клиента), поля, черновое имя.
  Итог: 150 читают поля, 96 только пишут, 4 без чтения и записи.
- `protocol/commands/NEW-1.63.3.md` — таблица только новых id (79): 36 ответов
  сервера, 40 запросов клиента, 3 маркера; у 27 восстановлены поля.
- Черновые имена выведены из полей, а не из документированной семантики:
  `17` (action / battleId / message) — уведомление о действии в бою,
  `2002`/`2003`/`2006` — команды по battleId, `10169` — version, `17001..17128` —
  семейство `serviceResult`.

## Что принципиально не выводится статически

1. Семантика ~25 команд-«пустышек» (`payload` нет): 146, 160-164, 167, 1008,
   7003, 7011, 7105, 7115, 7120, 7123, 7125, 7209, 10160-10164, 10167, 10168.
   Это либо подтверждения, либо команды, чьи аргументы задаются на стороне
   вызывающего кода. Имя = место вызова в UI.
2. Структуры, у которых поля не читаются напрямую (`readBytes` + ручной разбор):
   их формат задаётся вложенным `ByteArray`.
3. Preloader 1.63.3 — не нужен (см. выше).
